# Бизнес-анализ проекта: ИИ-аналитический центр для PR/GR (кейс GS Labs)

## 1. Бизнес-анализ (Business Understanding)

### 🔹 Коммуникации
| Тип контакта | Значение                          | Комментарий                              |
| --- |-----------------------------------|------------------------------------------|
| Исполнитель | Команда хакатона (контакты в TT)  | Основной канал — чат команды             |
| Кейсодатель | GR-менеджер GS Labs | Q&A день 2, чекпоинт день 4 |
| Носитель проблемы | Специалист, ведущий Excel-реестр | Интервью запланировано после защиты |
| Куратор потока | Ориентиры метрик (время/качество) | Жёстких порогов намеренно не фиксировали |

### 🔹 Бизнес-цель проекта
Создать ИИ-аналитический центр, который закрывает **большую работу**:
«вовремя заметить регуляторное/рыночное изменение и отреагировать до того, как оно
стало риском или упущенной возможностью», автоматизируя под работу
«собрать дайджест/обновить реестр, не пропустив важное».

Две ценности (по инсайту кейсодателя, риск-менеджмент — главная):
1. **Риск-менеджмент**: не пропустить критичные НПА — цена ошибки от штрафов
   (до 4 млрд ₽ по карточке №33 реестра) и приостановки сервиса до уголовной
   ответственности.
2. **Точки роста**: льготы для ИТ, федпроекты, гранты (карточки №6, 8, 20 реестра).

**Целевой эффект (гипотезы для валидации, ориентиры куратора):**
- утренний разбор суточной повестки: 10–15 минут (baseline: 3–4 ч вручную);
- отсутствие пропусков критичных материалов;
- доставка материала ≤15 мин (СМИ/TG) и ≤1 ч (сайты регуляторов);
- обработка 1 публикации 10–15 сек; поиск/фильтры <1 сек.

*Примечание: пороги — ориентиры куратора, финализируются на пилоте с заказчиком.*

### 🔹 Существующие решения и их ограничения
| Решение | Как работает | Почему недостаточно |
| --- | --- | --- |
| Excel-реестр GS Labs (текущий процесс) | 46 карточек, методика К1–К6/Н1–Н4, ручные ячейки, обновление неделями | Всё вручную: сбор, сути, баллы, переносы; эпизодично; нет алертов и дедупа; «неудобно и ДОЛГО» |
| Медиалогия / СКАН-Интерфакс | Охват СМИ/соцмедиа, алерты, отчёты | Дают охват и измерения, не дают готовый дайджест и скоринг «насколько важно для GS Labs» |
| КонсультантПлюс / Гарант | Полнота НПА, дайджесты изменений | «Что изменилось» без «что это значит для бизнеса»; нет СМИ/TG и отраслевого контекста |
| Brand Analytics | Уже куплено кейсодателем | По словам кейсодателя: «не решает основную задачу» — аналитику для управленческих решений |
| Meltwater | AI-саммари (Mira), глобальный лидер | Дорого, слабо в РУ-регуляторике, cloud-only |

**Наше отличие:** единый поток СМИ+НПА+TG; LLM-аналитик;
методика заказчика как конфигурация (К1–К6/Н1–Н4); lifecycle-трекинг НПА;
human-in-the-loop (ранжирование остаётся за специалистом).

| Тип | Статус | Комментарий |

### 🔹 Риски и план смягчения
| Риск | Вероятность | Влияние | План смягчения |
| --- | --- | --- | --- |
| Не уложиться в сроки хакатона | Средняя | Высокое | Один сквозной сценарий (lifecycle НПА); правило 4 вопросов при отборе фич |
| Парсинг Telegram нестабилен | Высокая | Среднее | Адаптер на источник + fallback на RSS/файлы дайджестов; ручное добавление (CRUD) |
| У регуляторов нет API | Высокая | Среднее | Парсеры + fallback; карточка создаётся вручную, lifecycle ведётся системой |
| Галлюцинации в саммари | Средняя | Высокое | Ссылка на оригинал у каждой карточки; запрет «додумывания» в промпте; человек-редактор; eval фактологичности |
| Качество категоризации <80% | Средняя | Высокое | Декомпозиция в К1–К6 (0–3 по критерию); few-shot примерами из реестра; итерации промптов с eval-скриптом |
| Специалист не доверяет саммари (RAT) | Средняя | Критическое | Режим валидации, а не переписывания; объяснимость («почему важно» = раскладка К1–К6); правка в один клик; хронометраж с 2–3 людьми |

### 1.2 Решаемые задачи с точки зрения аналитики (Data Mining goals)

### 🔹 Технические цели
| Задача | Описание |
| --- | --- |
| Саммаризация | 3–5 предложений + сущности (кто/что/когда/последствия) на русском |
| Категоризация | Темы: регуляторика/репутация/конкуренты/тренды + важность: high/med/low (и категории реестра «Незначительное…Критическое») |
| Дедупликация | Дубли одной новости — в одну карточку (кластер с агрегированным саммари) |
| Lifecycle НПА | Стадии: проект → принят → действует с даты → архив; детект смены стадии + алерт + предложение переоценки К2 |
| Предварительный скоринг | К1–К6 / Н1–Н4 с объяснением; финальный ранг — за специалистом |
| Асимметричная приоритизация | Оптимизация под отсутствие самого дорогого сбоя: «критичное → низкий» = 0 |

### 🔹 Критерии успешности
- Все метрики качества/скорости;
- 100% обязательных требований кейса (сбор 3 категорий, саммари, категории/приоритеты,
  дашборд с фильтрами/поиском, CRUD источников и данных, MVP-демо);
- сквозной сценарий «утро специалиста» работает end-to-end на демо;
- воспроизводимость: промпты, конфиги методики и eval-скрипты версионированы в Git.
