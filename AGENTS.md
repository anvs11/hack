# AGENTS.md

## Назначение

Этот файл обязателен для любого человека или ИИ-агента, работающего в репозитории.
Сначала прочитайте `README.md`, затем `rules.md` и `contracts/openapi.yaml`.

## Постоянный контекст проекта

Следующие файлы образуют единый защищённый контекст проекта:

- `AGENTS.md` — процесс работы агентов и владельцы зон;
- `README.md` — назначение, структура и канонические команды запуска;
- `rules.md` — архитектурные инварианты и порядок изменения контекста;
- `CONTEXT_PACK.md` — продуктовый контекст, факты и проверяемые гипотезы;
- `contracts/openapi.yaml` — API и модели обмена;
- `contracts/examples/*.json` — эталонные payload-примеры;
- `data/seed/*.json` — воспроизводимый demo-набор.

Нельзя менять один из этих файлов изолированно, если изменение затрагивает
архитектуру, API, схему данных, seed или команды запуска. В том же коммите агент
обязан обновить все затронутые файлы постоянного контекста, включая
`CONTEXT_PACK.md`, если изменились продуктовые границы или архитектура. В отчёте перечислить,
что синхронизировано. Если контекст менять не потребовалось — написать это явно.

`README.md`, `rules.md` и `contracts/` меняются только отдельным согласованным
коммитом/PR. Не смешивать изменение контракта с реализацией фичи. До согласования
обоих инженерных контуров действующий контракт остаётся источником истины.

## Жёсткие инварианты

1. AI-анализ и решение специалиста хранятся раздельно и версионируются.
2. Новая версия не перезаписывает предыдущую.
3. Финальный приоритет назначает только специалист; AI даёт предложение.
4. Скоринг детерминирован: LLM предлагает критерии, обычный код считает итог.
5. События lifecycle НПА append-only; неверные переходы отклоняются.
6. СМИ и Telegram не являются официальным подтверждением стадии НПА.
7. Seed работает без сети, повторный импорт не создаёт дубли.
8. SQLite-файлы, секреты и `.env` не коммитятся.
9. Alembic в demo-MVP не используется: чистая SQLite создаётся через `create_all`.
10. Нельзя объединять ветку при падающем unit/E2E-тесте её модуля.

## Процесс работы

1. Изучить постоянный контекст и код своей зоны до изменений.
2. Проверить, не меняет ли задача архитектуру, API, seed или команды запуска.
3. Сделать минимальный работающий дифф без рефакторинга вне задачи.
4. Выполнить проверки из README и проверки изменённого модуля.
5. Проверить `git diff` и `git status`; не добавлять временные файлы.
6. В отчёте указать сделанное, проверки и синхронизацию постоянного контекста.

## Инженерные принципы

- Честность: не выдавать желаемое за сделанное; неизвестное обозначать явно.
- KISS/YAGNI: использовать существующий код, стандартную библиотеку и уже
  установленные зависимости; не создавать абстракции «на будущее».
- Причина важнее симптома: перед исправлением проследить поток данных до корня.
- Код должен быть легко заменить или удалить.
- Валидировать входные данные на границах доверия и не терять данные при
  преобразованиях.
- Временные артефакты хранить в `/tmp`, проектные — только в репозитории.
- Никогда не выполнять массовый `git add`; добавлять файлы точечно.
- Не пушить и не сливать изменения без явного поручения владельца.

## Ветки и интеграция

- `main` — интеграционная ветка;

- `feat/analyst-workflow` — контур инженера 2;

- `README.md` обновляется в интеграционном PR, кроме отдельного согласованного
  изменения постоянного контекста.
