# RegRadar: функции MVP, пользовательские сценарии и ручная проверка

Дата: 2026-09-06  
Назначение: единый отчёт для команды, чекпоинта и самостоятельного тестирования.

## 1. Итоговый статус

Основной функциональный контур MVP реализован:

```text
источник → сбор → нормализация → дедупликация → AI-анализ
→ решение специалиста → досье НПА → отчёт → Telegram
```

Система остаётся human-in-the-loop:

- AI предлагает категорию, приоритет, факты и основания;
- специалист подтверждает, исправляет или отклоняет анализ;
- публикация не подтверждает юридическую стадию НПА;
- lifecycle НПА меняется только вручную по официальной ссылке;
- semantic similarity не удаляет и не объединяет материалы без решения человека.

Функциональная готовность не означает, что целевые метрики качества уже достигнуты.
Точность категоризации, полнота распознавания НПА, отсутствие критических пропусков и
время утреннего разбора требуют отдельной проверки на датасете заказчика.

## 3. Функции и сценарии

### 3.1. Профиль, роли и режимы отображения

Backend хранит Telegram ID, имя, username, роль, режим, стартовые фильтры и права.
Роли: `gr`, `pr`, `manager`. Роль определяет разрешения, а режим отвечает только за
объём информации на экране. Любой пользователь может выбрать «Кратко» или
«Подробно», но не может повысить себе роль.

Ручной тест:

1. Открыть приложение.
2. В шапке переключить «Кратко»/«Подробно».
3. Перезагрузить страницу.
4. Убедиться, что выбранный режим сохранился.
5. В Telegram убедиться, что внизу отображается профиль текущего пользователя.

Ожидаемо: меняется плотность карточек, данные и права не меняются.

### 3.2. Управление источниками

Пользователь видит состояние каждого источника, добавляет RSS/сайт/Telegram/file,
редактирует имя и URL, включает или выключает сбор, запускает один источник или все
включённые источники.

Ручной тест:

1. Открыть «Источники».
2. Добавить тестовую RSS-ссылку.
3. Изменить название.
4. Выключить и снова включить источник.
5. Нажать сбор одного источника.
6. Нажать общий сбор и проверить отчёт `created`, `already_seen`,
   `content_duplicates` и ошибки по каждому источнику.

Ожидаемо: повторный сбор уже известных записей не создаёт новые публикации.

### 3.3. Автоматический сбор каждые 15 минут

Отдельный worker сразу выполняет проход при запуске, затем повторяет его с интервалом
900 секунд. После сбора он запускает ограниченную пачку AI-анализов и Telegram-
доставку.

Ручной тест на сервере:

```bash
docker compose --env-file deploy/.env -f deploy/compose.yaml ps
docker compose --env-file deploy/.env -f deploy/compose.yaml logs --tail=100 collector
```

Ожидаемо: collector имеет статус `Up`, в логах появляются последовательные отчёты.
Заявлять доставку «до 15 минут» можно только после длительного измерения на новых
материалах, а не по одному запуску.

### 3.4. Одна карточка события и несколько первоисточников

Exact-дубли определяются по source/external ID, canonical URL и SHA-256 текста.
Второй URL того же текста сохраняется как дополнительный первоисточник одной
канонической публикации.

Ручной тест:

1. В «Мониторинге» открыть карточку с несколькими источниками.
2. Нажать «Первоисточники».
3. Проверить названия, даты, отметку главного источника и рабочие ссылки.
4. Вернуться в ленту и убедиться, что событие занимает одну карточку.

### 3.5. Мониторинг, поиск и фильтры

Лента сортируется от новых публикаций к старым. Доступны поиск, источник, тип
источника, категория, предлагаемый приоритет и очередь проверки. Лента обновляется
каждые 15 минут.

Ручной тест:

1. Убедиться, что верхняя карточка новее нижней.
2. Ввести слово из заголовка в поиск.
3. Применить категорию и приоритет.
4. Открыть «Требует проверки».
5. Сбросить фильтры и проверить восстановление списка.

### 3.6. Карточка публикации

Страница читается последовательно: исходный материал → AI-анализ → решение
специалиста. Пользователю не показываются внутренние ID, prompt, модель и технические
артефакты.

Ручной тест:

1. Открыть публикацию.
2. Проверить исходный заголовок, текст, дату и первоисточник.
3. Ниже проверить summary, факты, сущности, категорию, приоритет и основания.
4. Переключить «Кратко»/«Подробно» и сравнить представление.

### 3.7. Ручное добавление и редактирование публикации

Пользователь добавляет отсутствующий материал, исправляет title/tags и скрывает или
возвращает карточку. Правки сохраняются как новые metadata revisions.

Ручной тест:

1. В мониторинге нажать добавление публикации.
2. Заполнить URL, заголовок, дату и текст.
3. Открыть созданную карточку.
4. Изменить заголовок и теги.
5. Скрыть карточку и проверить её отсутствие в активной ленте.
6. Открыть режим со скрытыми и вернуть карточку.

### 3.8. AI-анализ

Поддержаны replay, локальный Hugging Face и внешний OpenAI-compatible provider.
Live-модель возвращает summary из 3–5 предложений, факты, сущности, категорию,
приоритет, критерии, evidence и uncertainty. Evidence-цитата обязана существовать в
оригинале. Каждый повторный запуск создаёт новую неизменяемую версию.

Ручной тест:

1. Открыть реальную публикацию с достаточно длинным текстом.
2. Нажать «Повторить AI-анализ».
3. Дождаться результата или понятной ошибки provider.
4. Проверить 3–5 предложений summary.
5. Выбрать 1–2 evidence-цитаты и найти их дословно в исходнике.
6. Повторить анализ и убедиться, что старая версия осталась в истории.

Важно: успешный ответ доказывает связность pipeline, но не точность модели.

### 3.9. Приоритет и объяснимость

Внутри backend сохраняется воспроизводимая сумма шести критериев и hard flags.
Основной UI показывает словесный приоритет и причины, а не вводит пользователя в
заблуждение псевдоточным числом. Неполные критерии дают `needs_review`; hard signal
не позволяет опустить рекомендацию ниже высокого уровня.

Ручной тест:

1. Открыть публикацию с AI-анализом.
2. Проверить предлагаемый приоритет и текстовые причины.
3. Убедиться, что финальная оценка специалиста показана отдельно.
4. Для неполного анализа проверить метку необходимости проверки.

### 3.10. Решение специалиста и история

Специалист подтверждает, исправляет или отклоняет конкретную версию AI-анализа,
задаёт финальную категорию и приоритет. Решение append-only и не изменяет исходную
AI-версию.

Ручной тест:

1. Открыть карточку с анализом.
2. Выбрать «Подтвердить», «Исправить» или «Отклонить».
3. Задать финальные поля и комментарий.
4. Сохранить.
5. Открыть историю и сравнить AI-предложение с решением человека.

### 3.11. Смысловая дедупликация внутри карточки

Embedding-модель создаёт кандидатов на близость. Специалист выбирает `duplicate`,
`related` или `different`. Только подтверждённый duplicate схлопывается в одну
карточку с несколькими первоисточниками.

Ручной тест:

1. Открыть карточку, где есть блок проверки похожего материала.
2. Сравнить заголовки и фрагменты.
3. Выбрать один из трёх вердиктов.
4. Для duplicate вернуться в ленту и проверить одну карточку и несколько ссылок.
5. Для related/different убедиться, что публикации остаются отдельными.

### 3.12. Автоматические досье НПА

Если новая публикация явно содержит тип документа и номер, backend создаёт
проверяемый draft или связывает публикацию с уже существующим досье. Широкое слово
«регулирование» без номера не создаёт досье.

Ручной тест:

1. Запустить сбор или backfill в preview:

   ```bash
   .venv/bin/python scripts/backfill_regulatory_cases.py
   ```

2. Применить найденные кандидаты:

   ```bash
   .venv/bin/python scripts/backfill_regulatory_cases.py --apply
   ```

3. Открыть «Нормативные документы».
4. Найти карточку «Требует проверки».
5. Открыть её и проверить связанные реальные публикации.
6. Исправить название и номер, сохранить реквизиты.
7. Убедиться, что стадия сама не изменилась.

### 3.13. Lifecycle нормативного документа

Стадии: проект → внесён → принят → опубликован → вступил в силу → изменён/отменён.
События append-only. Telegram и СМИ могут быть связанным сигналом, но событие требует
официальный URL.

Ручной тест:

1. Открыть досье.
2. Выбрать допустимую следующую стадию.
3. Указать дату, официальный URL, тип источника и комментарий.
4. Сохранить.
5. Проверить новую стадию и событие в timeline.
6. Попробовать пропустить стадию или сделать обратный переход.

Ожидаемо: неверный переход возвращает 409 и ничего не записывает.

### 3.14. Отчёт и дайджест

Дайджест собирает важные материалы, изменения документов, очередь проверки и
действия пользователя. Доступны preview и выгрузка JSON/Markdown. Отчёт можно
собрать вручную из выбранных карточек.

Ручной тест:

1. Добавить несколько публикаций в отчёт.
2. Открыть «Отчёт» и проверить порядок и содержимое.
3. Скачать JSON и Markdown.
4. Открыть «Дайджест», переключить ручной/автоматический раздел.
5. Проверить важные сигналы, lifecycle и решения специалиста.

### 3.15. Telegram Mini App и доставка отчёта

Frontend получает `Telegram.WebApp.initData`, backend проверяет подпись и срок,
создаёт/обновляет профиль и разрешает персональные действия. Готовый отчёт приходит
обычным сообщением в чат с ботом; длинный текст разбивается на части.

Ручной тест:

1. Открыть бота `@reg_radar_product_hack_bot` в Telegram.
2. Нажать кнопку меню и открыть Mini App.
3. Перейти в «Отчёт» или «Дайджест».
4. Нажать отправку в Telegram.
5. Закрыть Mini App и проверить сообщение в чате.
6. Включить автоматический отчёт и выбрать минимальный приоритет.
7. После появления нового подходящего AI-анализа проверить одну доставку без повтора.

Открытие публичного URL в обычном браузере не является проверкой signed initData.

### 3.16. Публичный HTTPS-сервер

На CPU VPS работают backend, collector и Caddy/web. SQLite хранится в Docker volume,
секреты монтируются отдельными файлами, сервисы перезапускаются после сбоя.

Ручной тест:

```bash
curl -fsS https://regradar-demo.209-250-246-26.sslip.io/api/health
curl -fsS https://regradar-demo.209-250-246-26.sslip.io/api/sources
```

Ожидаемо: health возвращает `{"status":"ok"}`, сайт открывается по HTTPS.

## 4. Автоматическая проверка

Backend:

```bash
PYTHONPATH=. .venv/bin/pytest -q
```

Frontend:

```bash
pnpm --dir frontend run typecheck
pnpm --dir frontend run lint
pnpm --dir frontend run test -- --run
pnpm --dir frontend run build
```

Изолированный E2E:

```bash
pnpm --dir frontend run e2e
```

E2E использует временную БД и синтетические fixtures только внутри теста. Рабочая
SQLite и реальные публикации не изменяются.

## 5. Что не блокирует MVP, но остаётся после хакатона

- независимая разметка заказчика и quality benchmark;
- расширение парсинга полного текста официальных сайтов;
- измерение 24-часовой задержки доставки и пользовательского времени разбора;
- фоновые job/status вместо синхронных долгих операций;
- архив НПА после завершения жизненного цикла;
- постановка задач коллегам и отдельный аудит поручений;
- серверные версии полного web-дайджеста и email;
- production Postgres, очередь, мониторинг и резервное копирование по расписанию.

Это развитие продукта, а не причина откладывать демонстрацию текущего MVP.

## 6. Рекомендуемый сценарий защиты

1. Открыть Telegram Mini App и показать подтверждённый профиль.
2. В мониторинге показать свежую ленту и фильтры.
3. Открыть одну карточку с несколькими первоисточниками.
4. Показать grounded AI-summary и объяснимый приоритет.
5. Сохранить решение специалиста.
6. Открыть автоматически найденное досье НПА.
7. Исправить реквизиты и показать, что новость не изменила стадию.
8. Добавить официальное lifecycle event.
9. Сформировать отчёт и отправить его сообщением в Telegram.

Этот сценарий показывает главный результат: не поток новостей, а управляемый путь от
сигнала к проверенному решению.
