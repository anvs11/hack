# Проверка продуктовых и технических метрик

Статус: протокол v1 от 2026-09-06. Значения ниже — ориентиры заказчика, а не уже
достигнутые SLA. Каждый результат публикуется вместе с выборкой, средой, временем
замера и сырыми строками; отсутствующие измерения остаются отсутствующими.

## 1. Матрица приёмки

| Метрика | Ориентир | Как считаем | Что есть сейчас |
| --- | --- | --- | --- |
| Доставка обычного материала | до 15 минут | `collected_at - published_at`, отдельно RSS/Telegram, только после начала наблюдения без первоначального backfill | worker запускается каждые 15 минут; steady-state окно ещё не измерено |
| Доставка с сайта регулятора | до 1 часа | та же формула, отдельная группа `regulator` | один реальный регуляторный материал является ручным историческим backfill и для SLA непригоден |
| AI-обработка публикации | примерно 10–15 секунд | wall-clock от вызова analyzer до валидной `AnalysisVersion`; рядом обязательны success rate, ошибки и p50/p95 | live-smoke на 5 материалах: 3 успеха, 2 HTTP 500; успешные ответы 4,647–11,408 с |
| Поиск и фильтры | менее 1 секунды | p50/p95/max по отдельным сценариям ленты, поиска и комбинированного фильтра | локально 90/90 запросов успешны; p95 0,127–0,133 с |
| Утренний разбор | 10–15 минут | время от открытия суточной повестки до отметки «разбор завершён», плюс число карточек и ручных исправлений | не измерено; нужен тест со специалистами |
| Приоритет | accuracy от 80% | совпадение AI-приоритета с независимым финальным приоритетом специалиста; дополнительно macro-F1 и confusion matrix | независимой разметки пока нет |
| Критичный материал не попал в низкий | 0 ошибок `critical → low` | отдельная ячейка confusion matrix; если в выборке нет critical, метрика не рассчитана | не измерено; текущий replay smoke не содержит critical |
| Дубли схлопнуты | одна карточка на одно событие | fragmentation: сколько эталонных событий осталось в нескольких карточках; отдельно false merge разных событий | production-разметки групп пока нет |
| В summary нет новых фактов | 0 unsupported claims | специалист разбивает summary на атомарные утверждения и для каждого отмечает опору в оригинале | не измерено; дословные evidence quotes проверяются автоматически, но этого недостаточно |

**Факт:** локальная скорость API уложилась в ориентир на текущей базе и без
параллельной нагрузки.

**Факт:** успешные ответы Qwen в последнем smoke заняли меньше 15 секунд, но
успешно завершились только 3 из 5 попыток. Два запроса получили HTTP 500 примерно
через 30 секунд.

**Вывод:** следующий технический приоритет — не ускорение успешных ответов, а
надёжность inference: retry только для временных 429/5xx, счётчик попыток и
наблюдение на большей выборке.

**Открытый вопрос:** выполняется ли задержка доставки в steady state. Интервал
опроса 15 минут сам по себе этого не доказывает: влияют момент публикации внутри
цикла, задержка RSS/Telegram и сетевые ошибки.

## 2. Воспроизводимые технические замеры

### 2.1. API и задержка сбора

При запущенном backend:

```bash
.venv/bin/python scripts/measure_runtime_metrics.py \
  --api-base-url http://127.0.0.1:8000 \
  --database .local/live.sqlite3 \
  --requests 30 \
  --output-dir data/eval/results/runtime-smoke-v1
```

Команда создаёт `report.json` и `REPORT.md`. API-smoke последовательный и не
заменяет нагрузочный тест. Задержка существующих записей включает первоначальный
historical backfill, поэтому служит только диагностикой полноты timestamps.

Для честной проверки доставки нужно зафиксировать `T0`, оставить worker включённым
минимум на сутки и анализировать только материалы с `published_at >= T0`. В отчёте
показываем p50, p95, max, долю внутри ориентира и все ошибки источников отдельно по
`rss`, `telegram`, `regulator`.

Повторная команда через сутки:

```bash
.venv/bin/python scripts/measure_runtime_metrics.py \
  --published-since 2026-09-06T15:00:00+03:00 \
  --output-dir data/eval/results/runtime-steady-state-v1
```

Значение `T0` в примере нужно заменить фактическим временем начала наблюдения.

### 2.2. Live LLM

```bash
set -a
source deploy/.env
set +a
export HACK_LLM_API_KEY_FILE=deploy/secrets/llm_api_key
.venv/bin/python scripts/evaluate_live_analysis.py \
  --database-url sqlite:///.local/live.sqlite3 \
  --limit 30 \
  --output-dir data/eval/results/live-llm-latency-v4
```

Скрипт использует production-настройки модели и лимита токенов, но не пишет новые
версии анализа в БД. Обязательные поля отчёта: attempted/successful/failed/timeout,
p50/p95/max только по успешным запросам, число результатов до 15 секунд, валидность
3–5 предложений и grounded evidence.

## 3. Проверка качества после получения датасета

Перед прогоном исходный файл сохраняется без изменений, а нормализованные данные
фиксируются SHA-256. Разметка не должна строиться из ответов той же модели.

### 3.1. Категория и приоритет

Одна строка на публикацию в `data/eval/templates/quality_labels.csv`:

- `publication_id` связывает исходник, prediction и label;
- `expected_category` и `expected_priority` задаёт специалист;
- `annotator_id` обязателен;
- `notes` содержит короткое основание спорного решения.

После преобразования в действующий JSON-формат:

```bash
.venv/bin/python scripts/evaluate_analysis.py \
  --labels data/eval/quality-labels-v1.json \
  --predictions data/eval/predictions-v1.json \
  --publications data/eval/publications-v1.json \
  --output-dir data/eval/results/quality-benchmark-v1
```

Решение о 80% принимается по priority accuracy. Category accuracy показывается
отдельно. `critical → low = 0` является самостоятельным guardrail и не может быть
скомпенсирован высокой общей accuracy. Если critical-примеров нет, честный статус —
`not_measured`.

### 3.2. Дедупликация

Специалист отмечает пары как `duplicate`, `related` или `different` в
`data/eval/templates/dedup_labels.csv`. Для интерфейсного обещания «одно событие —
одна карточка» дополнительно назначается `event_group_id` каждой публикации.

Считаем два независимых риска:

1. fragmentation — одна эталонная группа осталась в нескольких карточках;
2. false merge — в одну карточку попали разные эталонные группы.

Порог cosine similarity подбирается только на train/dev-части. Итоговые precision,
recall и ошибки объединения считаются на отложенной части без изменения порога.

### 3.3. Фактологичность summary

Автоматическая проверка дословных `evidence.quote` остаётся первой защитой. Для
самой метрики специалист заполняет `data/eval/templates/summary_claims.csv`: одно
атомарное утверждение summary на строку, `supported=true/false`, подтверждающая
цитата или комментарий. Результат — число и доля unsupported claims, плюс список
публикаций хотя бы с одним новым фактом.

## 4. Пользовательский тест утреннего разбора

Для каждой сессии заполняется `data/eval/templates/morning_review_sessions.csv`.
Сценарий фиксированный:

1. специалист открывает суточную повестку с одинаковыми стартовыми фильтрами;
2. просматривает карточки, раскрывает первоисточники и исправляет AI при необходимости;
3. завершает разбор явной отметкой;
4. записываются длительность, число просмотренных карточек, исправлений, пропущенных
   критичных событий и субъективная оценка полезности.

Для сравнения нужен тот же специалист и сопоставимая суточная повестка без сервиса
или его обычное зафиксированное время. Пока таких сессий нет, формулировка
«сократили разбор до 10–15 минут» недопустима.

## 5. Минимальный пакет для защиты

- `runtime-smoke-v1/report.json` — API и диагностический collection lag;
- `live-llm-latency-v3/report.json` — latency вместе с failure rate;
- `quality-benchmark-v1/report.json` и `rows.csv` — после независимой разметки;
- dedup report на реальных размеченных парах/группах;
- summary claims report;
- минимум несколько строк реального пользовательского хронометража.

До появления соответствующего артефакта в презентации используем формулировки
«ориентир», «локальный smoke» или «не измерено», а не «достигнуто».
