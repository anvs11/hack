# Промпт для GPT-6 Astra: редизайн RegRadar

Скопируй текст от «Ты работаешь…» до конца файла в задачу GPT-6 Astra с доступом к репозиторию `hack`. Это задание на реализацию, а не на подготовку ещё одного плана.

---

Ты работаешь как продуктовый дизайнер и frontend-инженер в существующем репозитории. Реализуй полный редизайн frontend: преврати текущий Insight в **RegRadar**, ежедневный аналитический инструмент PR/GR-специалиста для мониторинга регуляторных и репутационных новостей.

Главный сценарий: **настроить фильтры → получить список карточек новостей → открыть материал и изучить AI-анализ → добавить выбранные новости в отчёт для менеджера → проверить и выгрузить отчёт**.

## 3. Референсы и художественное направление

Референсы: [trendHERO](https://trendhero.io/ru/) и [MPSTATS](https://mpstats.io/).

Изучи доступные страницы визуально. Это публичные маркетинговые страницы; не утверждай, что видел закрытые кабинеты. У trendHERO полезны показанные модульные аналитические карточки, фильтрация, переход к подробному анализу, списки и экспорт. У MPSTATS — понятное разделение инструментов и задач, выраженные цветовые акценты, объёмные детали. Возьми качество визуальной подачи и продуктовые принципы; не копируй рекламные страницы, формы лидогенерации, тарифы, отзывы, баннеры, попапы, чужие тексты, логотипы или изображения.

Направление RegRadar: **светлая профессиональная аналитическая среда с тёмной объёмной картой сигналов**. Ощущение современного исследовательского инструмента. Сначала ясность и скорость работы, затем визуальная выразительность.

- Основной фон холодный светлый; панели белые; основной текст графитовый; акцент электрический синий/индиго. Красный/янтарный имеют семантическое значение риска и внимания.
- 3D передаётся освещением сфер, перспективой, глубиной графа, мягкими тенями плавающих панелей. Полупрозрачность допускается в сцене и её обрамлении; под текстом анализа — стабильная читаемая поверхность.
- Базовый текст 14–16px, заголовок страницы 24–32px, заголовок новости 17–20px, читаемые метаданные от 12px. Основные тексты обычным регистром.
- Компактные интервалы по сетке 4/8px, панели с радиусами примерно 12–16px, аккуратные разделители. Выразительность строится на композиции, а не на разноцветных карточках.
- Логотип RegRadar: простой оригинальный SVG-знак радара/орбиты и wordmark. Обнови бренд, browser title, favicon и доступные имена в пределах frontend. Не переименовывай доменные модели и API.
- Убери рекламные слоганы, огромные пустые блоки, маркетинговый footer и обязательные анимации появления текста. Все экраны должны выглядеть частью одного рабочего приложения.

## 4. Структура и первый экран

Основная навигация: «Мониторинг», «Отчёт» со счётчиком выбранных материалов; ниже служебные разделы «Кейсы НПА», «Похожие публикации», «Источники». На desktop используй компактную боковую навигацию; сверху — название рабочей области и реальные состояния интеграций. Не показывай постоянно `Demo space` на реальных данных.

Сохрани `/feed`, `/publications/:id`, `/digest`, `/duplicates`, `/sources`, `/regulatory-cases/:id`. `/digest` становится рабочим конструктором отчёта. Автоматическая сводка остаётся доступной отдельной вкладкой внутри него. Убери жёсткую навигацию на `case-001`: список кейсов можно построить на существующем `api.listRegulatoryCases`; детали продолжают открываться по прежнему маршруту.

На `/feed` пользователь сразу видит заголовок «Мониторинг», поиск, основные фильтры и начало выдачи. Не ставь перед ними заставку или кнопку «Начать». На первом входе сразу загружай все активные публикации без узкого периода по умолчанию, чтобы старый demo-набор не оказался пустым. Фильтрация — главное доступное действие, но не обязательный барьер перед данными.

Desktop-композиция: навигация 200–220px, рабочая область с фильтрами вверху, ниже вертикальный список карточек; справа компактная панель 3D-карты примерно 300–360px шириной. На 1280×720 и 1440×900 поиск, ключевые фильтры и хотя бы одна полноценная карточка должны быть видны без прокрутки. Карта начинается в верхней рабочей зоне и не вытесняет фильтры и новости. На узких экранах карта свёрнута в «Карта сигналов», фильтры раскрываются в доступной панели. Список — основной режим всегда.

## 5. Фильтры и выдача

Используй существующий `GET /api/publications`:

| Интерфейс | Параметр API |
| --- | --- |
| Поиск | `q` |
| Источник / тип | `source_id` / `source_type` |
| Период публикации | `published_from` / `published_to` |
| Категория AI | `category` |
| Приоритет AI | `proposed_priority` |
| Флаг обязательной проверки AI | `needs_review` |
| Видимость | `visibility=active|hidden|all` |
| Страницы | `limit`, `offset` |

В основной строке размести поиск, период, категорию, приоритет AI; остальные параметры — в «Все фильтры». Используй реальные enum и названия источников. Добавь быстрые периоды «Сегодня», «7 дней», «30 дней», «Всё время», активные фильтры с индивидуальным удалением, сброс и счётчик `total`. Даты переводи в границы дня выбранного/показанного часового пояса, не теряй последний день, проверяй обратный диапазон.

`needs_review=false` не означает «Проверено специалистом» и не доказывает достоверность AI. Подписи: «AI требует проверки» / «AI не выставил флаг проверки». Отдельного серверного фильтра актуального человеческого решения пока нет. Не подменяй один другим.

Поиск с debounce около 300ms, фильтры применяются предсказуемо. Применённое состояние и пагинация в URL, Back/Forward восстанавливают их. При изменении критериев сбрасывай `offset`; отменяй устаревшие запросы, исключи гонки. При возврате из новости восстанавливай позицию ленты.

Реализуй настоящую пагинацию на весь `total` (лимит API не более 100), а не только первые 20 новостей. В MVP сохраняй серверный порядок и подпиши его «Сначала высокий приоритет AI». Не предлагай глобальное «Сначала новые», сортируя лишь текущую страницу. Потребность в альтернативной серверной сортировке вынеси в backend-документ. Счётчики отдельных категорий не выводи как статистику всей базы, если рассчитана лишь загруженная страница.

Карточки — компактные горизонтальные статьи, которые удобно просматривать сверху вниз:

1. Источник, тип источника, дата и время публикации.
2. Содержательный заголовок-ссылка, краткое содержание 2–3 строки; при отсутствии анализа — честно обозначенный фрагмент исходника.
3. Категория, явно подписанный приоритет AI, `importance_score` с диапазоном 0–18, если известен; статус решения человека отдельно.
4. Теги в разумном количестве с раскрытием остальных.
5. «Открыть анализ» и «В отчёт» / «В отчёте»; checkbox для пакетного выбора.

Не делай ссылку вокруг вложенных кнопок. Выбор карточек не открывает материал; добавление в отчёт не сбрасывает фильтры. Пакетное действие по умолчанию относится только к выбранным загруженным карточкам: никакого неявного «выбрать всю базу». Не нужны стоковые картинки к каждой новости.

## 6. Детальная новость и AI-анализ

Сохрани отдельную страницу с прямой ссылкой. Верх: возврат к результатам, заголовок, источник/дата, ссылка на оригинал, постоянная заметная кнопка добавления в отчёт.

Основной экран чтения: исходный материал и анализ в двух колонках на широком экране, последовательные секции или доступные вкладки на mobile. Не заставляй читать длинный исходник, чтобы добраться до AI-вывода.

Структура анализа: краткая суть (`summary`), факты (`facts`), сущности (`entities`), категория и предложенный приоритет, важность и шесть именованных критериев, основания (`evidence.claim` + `quote`), неопределённость и флаг проверки. Историю и технические сведения версии раскрывай по требованию. Текущая версия, тип replay/live и дата анализа должны быть различимы.

Не выдумывай влияние на бизнес, рекомендации, дедлайны, confidence или ROI. Показывай такие выводы только когда их реально содержит источник/анализ; пользователь может отдельно написать своё заключение для отчёта. `uncertainty` не переименовывай в точность модели. `null` показывай как «Нет данных», не как 0.

AI-анализ и решение специалиста — отдельные секции. Финальный приоритет устанавливает только специалист через существующий API. Решение актуально для текущего анализа только если `latest_decision.analysis_id === latest_analysis.id`; старое решение пометь как относящееся к предыдущей версии. Сохрани confirmed/corrected/rejected без смешения отклонённого анализа с подтверждением.

Сохрани создание новой версии анализа, историю, исправление title/tags, скрытие/восстановление, решение специалиста, привязку к НПА. Вторичные операции собери в понятные меню и раскрываемые секции. Не запускай новый AI-анализ автоматически при открытии страницы. Сохрани правила официального подтверждения lifecycle НПА и существующую Telegram-аутентификацию.

## 7. Отчёт для менеджера

Реализуй **один полноценный локальный черновик** без ожидания backend. Пользователь добавляет/удаляет новости из ленты, детали и списка выбранного, видит единый счётчик и сохраняет отбор при смене фильтров, страниц и перезагрузке браузера.

Используй общий frontend-store и версионированное браузерное хранилище. Дедупликация по `publication.id`. Храни выбранные ID, порядок, комментарии пользователя и снимок использованных данных/ID версий анализа и решения. Одинаковая новость добавляется один раз. Ошибка/quota/повреждённый JSON в хранилище не должны ломать приложение; при невозможности сохранить явно сообщи, что черновик доступен только в текущей сессии. Разделяй черновики разных подтверждённых пользователей и источников данных/demo-режима.

На `/digest`: название отчёта, дата формирования, короткое резюме автора, выбранные материалы с порядком и комментариями, предпросмотр и экспорт. Разреши менять порядок кнопками вверх/вниз; drag-and-drop необязателен. Для каждого материала: источник и ссылка, дата, summary, версия анализа, отдельно AI-приоритет и актуальное решение человека. Непроверенные материалы можно добавить, но они остаются явно непроверенными и в экспорте. Комментарий для менеджера не создаёт `SpecialistDecision`.

Снимок не должен незаметно меняться после нового AI-анализа. При повторном чтении публикации сообщи о новой версии и предложи явное обновление снимка с сохранением комментариев. Для недоступной/скрытой новости сохрани локальный снимок и покажи её состояние, не удаляй автоматически.

Реальные действия: скачать Markdown и JSON, открыть подготовленный печатный вид для сохранения в PDF средствами браузера. Не имитируй серверный PDF-экспорт. Печатный вид: RegRadar, название, резюме, материалы, источники и маркировка AI/проверки; без sidebar, кнопок, графа и тёмного фона. Экранируй недоверенные данные, не вставляй исходники через небезопасный HTML.

Короткая полезная подпись: «Черновик сохранён в этом браузере». Не обещай совместный доступ или отправку менеджеру. Серверное хранение, версии, шаринг и доставка — задачи backend. Сохрани существующую автоматическую сводку отдельной вкладкой и не добавляй автоматически все её материалы в ручной отчёт.

## 8. 3D-карта сигналов — функциональный визуальный акцент

Переосмысли текущую WebGL-сеть как «Карту сигналов»: **один узел = одна реальная новость из текущей загруженной выдачи**. Реализуй красивую объёмную сцену с небольшими освещёнными сферами, тонкими связями, спокойной глубиной и ясным состоянием выделения.

- Координаты детерминированы по ID и не пересоздаются случайно при каждом рендере. Раскладка может группировать узлы по категории; это композиция, а не доказанная связь.
- Цвет обозначает категорию с легендой, небольшой ореол — высокий/критический AI-приоритет; отметка выбора — включение в отчёт. Не превращай неизвестную важность в минимальную.
- Hover/focus показывает заголовок, источник, дату, приоритет. Click/Enter на узле открывает ту же детальную новость; синхронизируй выделение узла и карточки.
- Рёбра допустимы только при объяснимом основании в доступных данных, например «Общая сущность: …» или «Общий тег: …». Нормализуй строковые совпадения, ограничь число рёбер. Не рисуй случайные связи и не называй совпадение тега причинной связью или доказанным дублем. Если оснований нет — показывай отдельные узлы.
- Карту строить из уже полученных данных, без отдельного GET на каждый узел и без загрузки всей базы. Подпись «На карте N из M найденных новостей»; при лимите узлов объясняй охват. Для MVP достаточно до 50 узлов.
- Плавный переход после фильтрации, подсветка выбранного, лёгкая управляемая перспектива. Без постоянного хаотичного вращения, перехвата прокрутки и анимации длинных текстов. Предусмотри паузу/сброс вида и сворачивание карты.
- Lazy loading, ограничение DPR, остановка рендера вне viewport и в скрытой вкладке, очистка WebGL-ресурсов и обработка context loss. `prefers-reduced-motion` отключает движение.
- При недоступном WebGL — осмысленная 2D-карта или компактный доступный список тех же новостей. На телефоне граф не загружается до раскрытия. Все действия доступны без canvas, hover и мыши.

Предпочти развитие собственного `HeroVisual` или небольшой заменяемый renderer. Новую 3D-зависимость добавляй только при конкретной необходимости, с локальным lockfile frontend и обоснованием веса. Не подключай тяжёлую библиотеку ради декоративных шаров. Граф не должен блокировать ленту при сбое.

## 9. Состояния, адаптивность и честность

Для ленты, детали и отчёта реализуй loading, error с повтором, empty, частичную ошибку и восстановление. Различай «Нет публикаций» и «Ничего не найдено по фильтрам». Ошибка источников или карты не скрывает успешно загруженные новости. При обновлении сохраняй полезный контент, но обозначай, если он относится к предыдущей выборке.

При отсутствии backend показывай ошибку подключения; MSW/demo включается только существующим явным dev/test-механизмом. Не маскируй сбой API красивыми фиктивными данными. Не показывай «Live» без основания.

Проверь 1440×900, 1280×720, 768×1024 и 390×844. Нет горизонтального скролла страницы, обрезанных контролов и перекрытых действий. Видимый focus, семантические labels, клавиатурная навигация, контраст WCAG AA, touch-target около 44px на mobile, возврат фокуса после закрытия панелей.

## 10. Порядок выполнения и приёмка

Сначала изучи приложение и запусти доступный локальный frontend. Зафиксируй короткий план и реализуй работу целиком. Не останавливайся после макета или изменения цветов. Последовательность: оболочка и токены → фильтры/выдача/пагинация → детали → общий отбор и отчёт → граф → остальные экраны → проверки.

Переиспользуй существующие API, форматтеры, тесты, loader и экспортные функции там, где их семантика подходит. Обнови frontend-дизайн-систему и demo-сценарий. Новый ручной отчёт не должен менять смысл старого автоматического снимка. Не удаляй проверки инвариантов ради зелёных тестов.

Запусти из корня `hack`:

```bash
npm --prefix frontend run generate:api
npm --prefix frontend run typecheck
npm --prefix frontend run lint
npm --prefix frontend run test -- --run
npm --prefix frontend run build
npm --prefix frontend run e2e
```

Изучи E2E-runner до запуска; любые необходимые backend-процессы/данные для проверки используй только в изолированном тестовом режиме, без изменения исходников и рабочих БД. Если среда не позволяет проверку, опиши конкретную причину и выполненные альтернативы. Не утверждай, что тест прошёл, если он не запускался.

Покрой существенные сценарии: фильтры и URL Back/Forward; больше одной страницы результатов; возврат из детали; добавление/удаление без дублей; отбор через пагинацию; восстановление черновика; актуальный/устаревший/rejected decision; новая версия анализа в отчёте; `null`; ошибка storage; export выбранного; переход из узла; fallback графа. Визуально проверь ключевые экраны в браузере на указанных размерах.

Задача готова, если:

1. Пользователь сразу видит фильтры и новости; крупный рекламный hero отсутствует.
2. Можно пройти весь путь от фильтрации до экспорта выбранных материалов без потери состояния.
3. RegRadar последовательно оформлен на всех страницах, в title/favicon и печатном отчёте.
4. Каждый узел карты открывает реальную новость; связи и охват данных объяснимы.
5. AI и решение человека различимы; недостающие данные не выдуманы.
6. Существующие операции анализа, решения, НПА, источников, дублей и Telegram сохранены.
7. Изменения ограничены разрешёнными файлами; backend и контракт не изменены.
8. Backend-потребности оформлены отдельно с приоритетами и критериями приёмки.

В финале дай краткий отчёт: что реализовано, какие файлы изменены, какие проверки реально прошли, что пока локально и что требуется backend. Укажи, что protected context не менялся, приложи доступные скриншоты ключевых экранов. Не пушь, не деплой и не сливай изменения без отдельного поручения.
