# RegRadar: ограничения API и предложения по развитию

Составлено после реализации и проверок frontend, 6 сентября 2026 года.
Источник истины — действующий `contracts/openapi.yaml`. Этот документ содержит
предложения для обсуждения с владельцем backend; он не расширяет контракт.
В коде RegRadar нет вызовов предлагаемых ниже endpoint. Backend, БД и схемы
не менялись.

## Что работает на текущем API

Для выполненного задания с локальным отчётом обязательных изменений backend нет.
Проверки прошли на настоящем локальном API с изолированной временной SQLite.

| Сценарий | Использованная возможность | Решение frontend |
| --- | --- | --- |
| Мониторинг | `GET /api/publications`: q, source_id, source_type, published_from, published_to, category, proposed_priority, needs_review, visibility, limit, offset и total | URL-фильтры, включительный последний день, отмена устаревших запросов, серверная пагинация и порядок |
| Исследование | Деталь публикации, история, существующие операции анализа, metadata и решений | Отдельные AI и специалист, актуальность по analysis_id, без автоматического запуска AI |
| Список кейсов | `GET /api/regulatory-cases` и деталь кейса | Навигация к реальным кейсам вместо жёсткой ссылки на case-001 |
| Карта | Уже полученные элементы текущей страницы | До 50 узлов, объяснимые общие теги/сущности и отключаемые связи по source_id, без дополнительных запросов и случайных связей |
| Ручной отчёт | Полные PublicationDetail и источники из существующих read API | Версионированный localStorage со снимками, порядком и комментариями; Markdown, JSON и печать |
| Проверка обновлений отчёта | `GET /api/publications/{id}` | До четырёх одновременных запросов, сравнение ID анализа/решения, revision ID и updated_at; обновление только по кнопке |
| Автоматическая сводка | Существующие read API публикаций, источников, кейсов и историй | Сохранён прежний клиентский сбор; отдельная вкладка, не наполняющая ручной отчёт |

Произвольной сортировки публикаций API не предоставляет. UI не добавляет параметр
sort и не переставляет только текущую страницу. `needs_review` — флаг анализа,
а не отметка проверки человеком. Отдельное серверное графовое API для текущей карты
не требуется.

## Необходимые изменения при переходе к нескольким пользователям

Ниже P1 означает необходимость для соответствующего следующего этапа продукта,
а не блокер готовности локального frontend. В текущем объёме P0-запросов нет.

### 1. Стабильная идентичность обычного браузерного пользователя

- **Пользовательский сценарий:** два специалиста по очереди входят в обычном
  браузере и видят собственные черновики; выход не раскрывает подборку другого.
- **Существующий API:** Telegram-аутентификация возвращает пользователя после
  серверной проверки initData. Общего механизма сессии обычного браузера и read API
  текущего пользователя в действующем клиентском контракте нет.
- **Чего не хватает:** подтверждённого principal для браузерного входа, жизненного
  цикла сессии и сигнала её смены/выхода. Переданный `author_id` не заменяет вход.
- **Временное решение:** ключ черновика разделён по API base URL/MSW и подтверждённому
  Telegram ID. До проверки Telegram используется отдельная неподтверждённая область.
  Обычный браузер имеет один локальный анонимный профиль. Другого человека в том же
  профиле невозможно надёжно отличить средствами текущего frontend.
- **Предлагаемое расширение:** согласовать аутентификацию браузера, чтение текущего
  пользователя и завершение сессии; связывать доступ к будущим отчётам с серверной
  идентичностью. Конкретный механизм и пути остаются решением владельца backend.
- **Приоритет:** P1, до запуска персональных отчётов для нескольких браузерных
  пользователей. Telegram-проверку подписи/срока сохранять.
- **Критерии приёмки:** смена пользователя A→B, выход, истечение сессии и перезагрузка
  не показывают отчёт A пользователю B; подмена ID на клиенте не даёт доступ;
  неподтверждённый Telegram initData не создаёт авторизованную сессию.

### 2. Серверное хранение ручных отчётов с фиксированными версиями

- **Пользовательский сценарий:** продолжить подготовку на другом устройстве,
  восстановить работу после очистки браузера и открыть ранее подготовленную версию.
- **Существующий API:** доступны публикации, анализы и решения; ресурса ручного
  отчёта, его владельца, состава и версий нет. Автоматическая сводка также клиентская.
- **Чего не хватает:** сохранения названия/резюме, порядка материалов, комментариев,
  снимков и их версий; чтения владельцем, контроля конкурентного редактирования.
- **Временное решение:** один локальный черновик на область хранения. Снимок содержит
  данные публикации, AI, решения и источника; поздний анализ не меняет его. Квота или
  отказ localStorage дают предупреждение, повреждённый оригинал можно скачать.
  Нет синхронизации устройств и конфликтов между одновременно открытыми вкладками.
- **Предлагаемое расширение:** после согласования контракт ресурса reports
  (например, `/api/reports`, только предложение), владелец из проверенной сессии,
  revision/ETag, позиции материалов и неизменяемые снимки/ссылки на архивные версии.
  Явное обновление снимка должно сохранять пользовательский комментарий.
  Доставку менеджеру не включать автоматически в этот объём.
- **Приоритет:** P1, если требуется хранение за пределами текущего браузера.
- **Критерии приёмки:** один ID публикации не дублируется; порядок и комментарии
  восстанавливаются на другом устройстве; новая AI-версия не меняет старый отчёт;
  устаревшая запись получает конфликт вместо молчаливой перезаписи; недоступный
  материал не исчезает из сохранённого отчёта; экспорт сохраняет прежние статусы,
  включая отсутствие решения, отклонение и решение по предыдущему анализу.

## Необязательные улучшения

### 3. Пакетное чтение выбранных публикаций или метаданных их версий

- **Пользовательский сценарий:** быстро проверить обновления большой ручной подборки.
- **Существующий API:** деталь читается по одному ID; list поддерживает фильтры и
  страницы, но не точный набор выбранных ID.
- **Чего не хватает:** одного ограниченного пакетного ответа с независимым статусом
  каждого элемента. Сейчас количество запросов растёт вместе с подборкой.
- **Временное решение:** очередь максимум из четырёх одновременных GET; ошибки
  отмечаются на конкретных карточках, сохранённые снимки остаются доступны.
- **Предлагаемое расширение:** согласовать ограниченный список ID для пакетного read
  или лёгкий ответ с analysis_id, decision_id, revision_id, updated_at. Полные данные
  получать только для явного обновления; ошибка одного ID не обнуляет весь ответ.
- **Приоритет:** P2, оптимизация после измерения задержек на реальных подборках.
- **Критерии приёмки:** задокументированы лимит и поведение повторных ID; для каждого
  ID определён результат доступности; версии совпадают с детальным GET; ответ не
  вынуждает скачивать всю базу, частичные ошибки корректно показываются в редакторе.

### 4. Согласованный снимок выдачи при изменениях между страницами

- **Пользовательский сценарий:** пройти несколько страниц активного мониторинга,
  пока другие специалисты запускают анализы и меняется серверный приоритет.
- **Существующий API:** limit/offset и текущий total; порядок по приоритету, дате и ID.
  Токена снимка или cursor, фиксирующего выдачу, нет.
- **Чего не хватает:** гарантии неизменного состава и порядка между запросами.
  Это ограничение offset-пагинации при изменяемой сортировке, а не обнаруженная
  ошибка сортировки текущего backend. Нагрузочный сценарий не проверялся.
- **Временное решение:** точное сохранение query/offset в URL, серверный порядок и
  защита от гонок; выбранные материалы дедуплицируются по ID. Возврат восстанавливает
  позицию, но не обещает замороженную выдачу после изменения данных на сервере.
- **Предлагаемое расширение:** при подтверждённой потребности согласовать snapshot
  token либо cursor и правила его жизни совместно с фильтрами и total.
- **Приоритет:** P3, после наблюдения проблемы в совместной работе.
- **Критерии приёмки:** тест с изменением приоритетов между страницами определяет
  стабильное поведение без необъяснимых пропусков/повторов; истечение токена имеет
  явную ошибку и путь обновления; старые запросы limit/offset сохраняют совместимость.

## Что не запрашивается

Нет оснований добавлять выдуманные метрики точности, финансовые эффекты,
автоматические рекомендации, отдельный сервис 3D, глобальный граф всей базы,
автоматическое объединение дублей или изменение lifecycle НПА.
Серверная доставка и совместный доступ к отчётам не входят в выполненное задание.
Перечисленные предложения требуют отдельного согласования и синхронизации
защищённого контекста по `AGENTS.md`; frontend-редизайн такого согласования не заменяет.
